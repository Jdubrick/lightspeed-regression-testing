Proposed design

Black-box regression testing for LCORE

A small Python suite tests an already-running LCORE instance through HTTP and SSE. The caller owns deployment. The suite owns protocol checks and evidence.

  • Python 3.12
  • pytest
  • locked dependencies
  • no runner image for the PR gate
  • optional MCP profile

Architecture

One narrow boundary

The suite receives a URL and a profile. It never starts LCORE, copies product configuration, or handles provider credentials.

Release flow

From image bump to merge gate

The same test command works against Compose, OCP, or a developer-run instance.

01

Open bump PR

Automation updates the LCORE image on the release branch.

02

Prepare runtime

The configs workflow starts LCORE, its provider, and selected fixtures.

03

Run pinned suite

CI checks out a fixed test commit and installs its locked Python environment.

04

Test through LCORE

pytest exercises public APIs. MCP and provider internals remain behind LCORE.

05

Publish and clean up

JUnit and diagnostics become artifacts. The caller removes the environment.

Test policy

Profiles select capabilities

Missing requested dependencies fail during preflight. Tests do not silently skip required coverage.

MCP

MCP is an environment capability

LCORE must already point to the test MCP server before MCP tests run. The server uses a pinned version, deterministic tools, and known test credentials. pytest reaches it only through LCORE.

The suite owns

  • HTTP and SSE protocol behavior
  • Reusable assertions and polling
  • Capability-based test selection
  • Redacted diagnostics and JUnit
  • Unit tests for its own parser code

The caller owns

  • LCORE lifecycle and configuration
  • Model provider and credentials
  • RAG content and MCP fixture
  • Network access and storage
  • Service logs and final cleanup

Language

Python is the practical choice

The boundary matters more than the language. Python happens to fit LCORE’s API and the existing team knowledge well.

Recommended

Python and pytest

Strong HTTP and streaming support, concise fixtures, readable parameterization, and an easy migration path from the current suite.

TypeScript and Vitest

A sound choice for a JavaScript-heavy owning team. It offers good schema tooling but no clear advantage for this API suite.

Go

Useful when a single portable binary is a hard requirement. More code is needed for fixtures, assertions, and test reporting.
